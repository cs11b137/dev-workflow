# 场景：UI 变化（原型先行）

先在原型里定稿并经用户确认，再改真实应用。

## 阶段一：原型

1. 读 `designs/<app>/README.md` 与 `designs/<app>/AGENTS.md`（设计系统、模块纪律、预览、验证）。
2. 只改 `designs/<app>/`。照规格做的地方在注释里写小节号（如 `product-design §4.6`）。
3. 跑局部协议「验证」里的全部命令（构建、测试、设计系统检查），再用 HTTP 预览打开每个受影响入口，检查目标状态、交互、控制台零报错。在 worktree 里要另起端口，并确认服务来自当前检出。
4. 提交原型改动。交付说明写明：「真实页面尚未改动，等待原型确认」，并逐条列出原型与规格的差异（小节号 + 差异）。
5. 停在这里等用户确认原型。

完成标准：验证命令全部通过、每个入口看过、用户明确确认。

**例外**：原型里没有对应界面的改动，或不改变设计的缺陷修复，可直接改实现，在交付说明里写明原因。仓库没有 `designs/` 时，同样跳过阶段一并写明。

## 阶段二：真实实现（确认后）

1. 按确认的原型修改 `docs/development-workflow.md` §3 表里的每个表面。复用公共组件，不复制目录。
2. 逐个表面审计：有对应功能就同步；没有就在交付说明写「不适用」及依据，不补占位实现。
3. 每个表面分别打开实际页面验证（主题、尺寸、弹层、键盘焦点按影响覆盖）。原型截图只能证明原型。
4. 任务授权改变产品行为时，同步产品设计对应小节；没有授权就报告差异，不改规格。

完成标准：§3 表里每个表面都有「已同步并验证」或「不适用 + 依据」。
